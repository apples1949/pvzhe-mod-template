# 模板升级的兼容报告

用于迁移交付。共享报告放在 docs 的相应兼容/迁移说明，原始对比证据留在本地 .work；报告不包含用户机器路径或游戏源码内容。

记录以下必要信息即可，不为每个无关宿主文件写报告：

- **目标与输入**：旧模板基线/提交，新游戏版本及发行摘要，源码是否参与、是否与发行版一致；缺失输入。
- **影响与改动**：各项旧/新差异、模板影响、修改文件、对应验证；明确无改动和未知项。
- **支持范围**：新版是否已实测，旧版是否仍支持及其证据；平台、引擎、SDK、Mod API 与清单版本分别记录。
- **验证结果**：工具测试、构建/包检查、真实运行与功能证据、干净玩家流程、Skills 格式与引用检查；日志和产物摘要对应当前构建。
- **Wiki 同步**：旧/新版本主题页、逐项核对范围、修改及无变化项、实测/静态/待验证状态、索引和 Skills 链接更新；不能把旧版运行证据改名为新版证据。
- **剩余问题**：未验收项、诊断、迁移限制或需要用户提供的输入；只分析/编译通过时不写“升级完成”。

对每项修改使用简洁的影响表：

| 能力/机制 | 旧证据 | 新证据 | 影响与修改位置 | 验证结果及 Wiki 页面/状态 |
| --- | --- | --- | --- | --- |

将可复用经验写进相关 Skill 的按需参考文件，主 SKILL.md 只保留重要流程与触发链接。普通玩家文档仍从发行版开始；维护者可选的源码分析流程留在升级 Skill 中。

## 触发边界回归

| 用户请求 | 应有行为 |
| --- | --- |
| “新游戏已发布，请把旧模板更新到这个发行目录” | 使用升级 Skill，保存旧基线并核对目标 |
| “请用这份新版源码适配模板，没有发行包” | 开始静态分析，标明发行版运行验收待补，不能宣称完成 |
| “游戏更新了，请帮我更新模板”，无路径 | 使用升级 Skill，询问新版源码或发行版目录，不猜测路径 |
| “使用 $pvzhe-template-upgrade 更新模板” | 明确升级意图已提供，仍需目标输入与版本证据 |
| “游戏更新了” | 不自动迁移；有必要时澄清用户是否希望更新模板 |
| “首次准备这个游戏的开发环境” | release-analyze，不能擅自修改整个模板基线 |
| “帮我加个按钮”或“Mod 加载失败” | guide/UI 或 verify 排障；除非用户明确要求版本迁移，不进入升级流程 |

UI 影响项另列旧/新控件路径或动态创建入口、布局/层级变化、显隐条件、结构/行为出处及实际运行覆盖；删除或空闲区域结论须有结构与行为依据，截图缺失不能作为删除证据。

对局布局另列模式/槽数/动态触发（如金币）及窗口尺寸的覆盖矩阵，核对事件是否触发重新布局；未验条件保留边界，不沿用旧版安全位置或只记录分辨率。
