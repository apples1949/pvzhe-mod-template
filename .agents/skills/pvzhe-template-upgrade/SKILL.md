# 随游戏版本更新模板

输入：明确的模板升级要求、当前模板及旧兼容基线、用户提供的新版源码目录或完整发行版目录。输出：兼容差异、必要修改、验证证据与新版支持范围。

1. 确认任务是“新版游戏与旧模板的兼容迁移”。仅提到游戏更新、开发新功能、首次 prepare 或遇到加载错误，不足以触发；明确请求使用本 Skill 也视为升级意图，但仍需目标版本证据。不自行下载、猜测路径或开始迁移。
2. 缺少新版输入时询问新版游戏项目源码目录或发行版目录，提供任一种即可；已有信息不重复询问。读取 [迁移流程](references/migration.md)，先保存旧基线，核对输入版本，再分析差异。
3. 源码只用于维护者内部机制分析；发行版可经 pvzhe-release-analyze/pvzhe-pck-extract 提取 PCK、程序集及资源证据。两者不一致时分别记录，不把源码分支或程序集版本当作已发布版本。只有源码时可继续静态适配，但不能宣称已完成发行版验收。
4. 依据影响表修改模板、构建/分析/验证工具、清单和示例；同步实际受影响的 README、兼容说明、Wiki、配方导航及 Skills；按 [Wiki 维护规则](../../../docs/wiki/maintenance.md) 逐页比较并更新版本、资源/API、操作路径、前置状态和验证边界。UI 占位与阶段规则从新版场景/实例、配置/动画及脚本行为重新核对，包含布局模式/切换、卡槽数量、金币等动态显示与事件覆盖，再进行运行验证；不能根据截图未显示删除旧控件或宣布区域空闲。保留最小模板定位，FeatureLab 是可选回归示例，不借升级增加无关功能或修改宿主游戏。
5. 用新版发行版完成适用的构建、安装与真实运行验证，并在干净模板副本中确认玩家流程不依赖源码。在新版 Wiki 中分别记录实测、静态确认和待验证项，不继承旧版实测标签；更新 Wiki 索引及 Skills 导航。记录旧版支持是否保留；证据不足的版本不标为兼容。详细验收与停止条件见迁移流程。
6. 按 [兼容报告](references/compatibility-report.md) 交付差异、修改和验证结论。机器路径、原始源码、PCK、宿主 DLL 和解包内容留在本地，不进入模板分发；相关 Skills 只更新规则与按需参考资料，不复制整份迁移日志。

涉及发行资源或预览变化时，同步 [缓存与捕获协议](../../../docs/resource-cache-and-capture.md)：新哈希启用新缓存，旧背景/透明组件不能自动沿用；源码分析不代替发行哈希校验。检查升级后的捕获分支、alpha/字体/尺寸、逻辑坐标及预览身份，记录未验组件范围。
