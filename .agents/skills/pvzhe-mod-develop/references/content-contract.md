# 资源与角色内容的接入契约

适用：资源修改、新角色、发射/护具、皮肤及地图制作。先读匹配发行版的 [内容接入配方](../../../../docs/wiki/0.30.0/content-authoring.md)，其中基础托管注册有运行证据；社区其余线索仍须逐项核验，来源和许可见 [功能提取清单](../../../../docs/community-skill-extraction.md)。无需游戏内模组编辑器，玩家输入仍为已发布游戏及自己的素材。

## 开始前只确认当前功能需要的契约

1. 匹配 [Wiki基线](../../../../docs/wiki/0.30.0/overview.md) 与本地release.json，复用PCK缓存；按注册键定位实际资源/实例/配置和相关发布DLL实现。公共签名只证明入口存在，不证明行为。
2. 区分修改原有资源、新注册内容与对局中临时改变实例。原版修改需明确overrides及冲突/禁用恢复；新增使用稳定自有Key及所需声明，不能拿旧身份伪装新角色。
3. 列出自有文件、宿主res://引用、包内相对引用、注册类别/键及依赖。社区候选布局如 `Resources/Projectiles/<Key>.tres`、`Resources/Maps/<Key>.tres`、`Resources/Characters/Plants|Zombies/<Key>/{Config,Packet,Scene,Sprite}/...`，仅作定位线索；具体路径段数、文件名和声明语义由当前发行核验。
4. 检查清单provides/overrides/contentEntries、资源路径推导、托管注册分别由谁处理。不把“已加入resources允许名单”当作已经加载或注册。场景NodePath应与真实节点声明、父路径、预期类型一致；文本匹配不足以证明场景可实例化。
5. 使用 [项目配置](../../../../docs/project-configuration.md) 及单DLL入口；当前构建器仍要求Runtime/ModAssembly.dll和required策略。需要纯资源包、额外DLL或新脚本通道时先补协议/工具支持，不删除检查来强行打包。包内不嵌入宿主DLL、源代码或整份游戏素材。

## 新角色的关键检查

优先评估“复制完整宿主骨架、修改自有配置、托管注册”的最小路线；复用宿主根类型无需仅为新身份新建 Companion 类。需要新托管子类时才调查 `metadata/mod_character_*` 与 `CompanionOnly`；本轮未验收该路线。共同检查：

- 壳场景的根类型、config与sprite路径、组件集继承，以及游戏真正用于创建角色的入口。
- 角色Key、配置name/saveKey、卡片与精灵键的对应关系，不假设一名角色只有一张卡。
- 复制原卡时重新确定自有卡的解锁策略；原版条件不可直接成为新Mod卡的条件。只处理自己的副本，需门槛时使用宿主Mod进度条件。
- 如需Companion，核对binding、声明路径、类型名、继承与构造条件；包内声明与DLL实际类型对应，缺失时记录失败/回退，不能把回退生成的原版角色当新角色通过。
- 普通C#入口不自动获得Godot自定义Node回调；需要源生成/绑定的行为要单独确认，不能把“能编译”当作引擎已驱动。

## 输出与验证边界

输出当前任务的最小资源/代码、注册和依赖清单，以及包/发行摘要。生成自有配置或必要差量并引用宿主；若某方案要求分发完整原版资源，与项目边界冲突时换方案，不默认复制。

先做结构、声明、编译和关键损坏负例，再按 [功能验收](../../pvzhe-mod-verify/references/feature-acceptance.md) 运行对应场景。包结构、实际注册、可见入口、业务效果与表现分别验；静态分析阶段如实列待验项，不因流程Skill已存在就宣称新能力已实测。只有明确的模板版本迁移才进入template-upgrade。
