# 设置声明、生效与保存一致性

结合已有设置流程与社区经验整理，来源见 [提取清单](../../../../docs/community-skill-extraction.md)。下列失效条件/内部调用属于发行核对线索，不能替代当前公开Settings契约。

| 状态 | 如何处理 |
| --- | --- |
| 声明 | key/type/default/range/enum options合法且唯一；按发布版实际支持字段检查，不把任意JSON键当宿主能力 |
| 保存值 | TrySave结果、错误与RestartRequired明确；不从用户点了按钮推断已经保存 |
| 生效值 | immediate刷新已存在实例，restart等待重启；不得把所有战斗参数都强制热生效 |
| 配置页草稿 | 与运行值分开，检查取消、并发保存、包身份变化与重新打开页面 |

优先订阅宿主Changed并管理生命周期，核对它究竟覆盖哪些项。事件未触发先查值是否变化、applyMode、订阅时机、包摘要与页面草稿，不直接得出“必须每帧轮询”。确需补偿同步时只检查相关状态，在必要更新点处理，不每帧拆建整个UI。

自有快捷面板如与宿主草稿共存，要按实际保存管道操作，避免外部写入导致指纹冲突。社区SavePlayerSettings/Draft等名称仅作调查入口；不默认反射私有UI字段或摘挂原版回调。注入现有页时核对节点所属Mod和页面实例，不只靠Reset_<key>之类重名锚点。

## 保存链与注入锚点的实测细节（用户实机记录，本模板待复核）

状态：以下来自用户对更早版本的实机调试，本模板只验证了正常保存与重启生效。用于"配置页里注入的自建控件保存不了/串到别的 Mod 面板"这类问题。

- **宿主保存链是"读所有行控件 → 写草稿 → 有差异才保存"**。所以只把新值写进控件、不触发保存是不会落盘的（草稿仍是打开页面时的快照）。配置页开着时，正确姿势是"写控件值 + 触发宿主保存按钮"，不要绕过页面直接调保存接口——那会撞上指纹校验（提示"配置已被其他操作修改"），并在关页时再弹一次"放弃修改?"。
- **触发保存按钮时不要判 `Disabled`**：因为草稿没感知到你写的值，按钮必然是禁用的；发信号才会走到回调、读到新值、产生差异并正常保存。这一点反直觉，是"写完控件没保存"的常见根因。
- **配置页没开时**（例如战斗中呼出自己的面板）才可以直接调保存接口，此时没有草稿冲突。
- **注入锚点不唯一**：不同 Mod 可能声明同名的设置键 ⇒ `Reset_<key>` 这类锚点在多个配置页同时存在，后注入的回调会覆盖先注入的 ⇒ 表现为"点我的按钮弹出别人面板"。注入前必须做归属校验（沿祖先找本页的归属标识，例如本 Mod 名开头的富文本），不能只按锚点名找。
- **配置页行结构**：锚点按钮与控件本体在同一个行容器内，找同行控件要从锚点的父节点往下递归；行内控件类型随声明类型不同（下拉/输入框/勾选）。值↔控件的读写映射是宿主私有的，Mod 只能直接操作控件本身。
- **劫持原生控件回调做"模式切换"不要用事件摘挂**：反复创建/订阅会让"摘一个剩 N 个" ⇒ 一次点击触发多次。改用"固定桥接委托 + 布尔分发"（只订阅一次、模式切换只改状态字段），或干脆只控制自己控件的显隐。

可离线校验声明时使用当前宿主规则与正/负/缺API夹具；缺校验入口时明确限制，不能拿社区工具旧版本结果兜底。当前仓库未捆绑社区settings-validate，格式检查不证明设置页和热生效成功。

新增验证按需覆盖非法声明、未知枚举、即时/重启、取消、冲突、重开页及重启持久化；异常不吞掉，输出实际失败阶段。
