# 先理解需求，再选择实现

先按 [Wiki 索引](../../../docs/wiki/README.md) 核对发行版本与摘要，再按需求路由到具体主题。匹配基线时沿用已确认的操作路径；仅对缺项、差异或失败点补充分析，不从零遍历游戏。静态确认和待验证内容不能冒充运行验收。

玩家不需要知道组件、接口或 Skill 名称。输出是足够明确的需求摘要、必要问题及制作路由，不是让玩家填写技术问卷。

项目定位是最小模板和通用制作指导。FeatureLab 仅是可选参考与实测证据；按当前需求选择必要功能，不把示例整套内容当作玩家默认要求。

创建新 Mod 时，在主题明确后按 [身份与发布规范](../pvzhe-mod-develop/references/identity-and-release.md) 主动拟定稳定 ID；名称建议须反映实际功能范围，不将单项功能扩称工具箱或综合增强；作者由用户指定。已有 Mod 添加功能不改身份。用户有分享/发布意图时先补齐并确认名称、作者、版本，再做发布检查；本地开发不为待确认署名阻塞无关工作。

1. 结合当前对话和项目识别业务效果、玩家可感知的表现/反馈与时序、使用场景、触发方式及作用范围。默认沿用宿主同类行为，不为方便调用接口擅自改变表现；用户明确指定特殊表现时尊重选择。方案会明显改变体验且无法合理推断时，用玩家语言澄清，不把动画/音效逐项变成必答问卷。保留已确认的选择，不重新询问已有答案。
2. 区分关键缺项与实现细节。缺项会改变玩家得到的功能，且不能从上下文合理推断时，先询问；资源路径、原版风格组件选型、事件订阅和清理由 AI 分析决定。不要先要求玩家选择原版组件。玩家用现有玩法作类比时，区分要复用的交互特征与未指定的表现，不整套照搬；出现位置、获得方式等会改变操作链的歧义须在实现前澄清。
3. 每轮优先问最影响方向的 1～3 个问题，使用玩家语言。用户只说“加个按钮”时，先问放哪里、点击做什么；文字可随后确认或依据用途建议。不要凭空实现一个按钮，也不要一开始询问字体、坐标、程序集等技术细节。
4. 对合理默认值简短说明后继续，不要求批准每个细节。对局右下角击杀数已有位置和内容，先分析统计口径；“所有敌方僵尸死亡”和“仅玩家造成的击杀”影响结果，无法推断时询问。不能把离场、读档或销毁默认为击杀。
5. 主动补齐由用途可推导的约束：战斗操作在战斗阶段可用、准备阶段隐藏、尊重暂停/模态、避让原版控件；不把这些常规判断交给玩家反复确认。将目标、场景、触发、效果及相关表现/时序、数据口径、持久化和正向/负向验收结果整理成简短摘要。未解决的关键问题保持待定；可先分析接口，但不开始依赖答案的实现。若多个用户需求可独立完成，继续不依赖缺项的部分。
6. 需求足够明确后按 [功能制作路由](references/feature-routing.md) 读取对应Skill。资源修改、新植物/僵尸、发射、护具、外观、地图、输入和包补丁各用专门入口，复杂需求按需组合；不把角色、地图和关卡混为同一制作流程。用户说“复刻某植物”时由plant-recreate统筹正常可玩链、行为依据和必要近似，不自行降级为动画导入；复刻僵尸由zombie-create组合共用复刻方案与来源Skill，只借外观才走skin。参数缺项先查材料与宿主类比，可合理补全的细节自主处理，关键分歧才问玩家。

组件复用由 AI 默认评估，读 [复用资料](../../../docs/reuse-catalog.md)。制作 Skill 若发现新歧义，返回此引导步骤；常规实现选择自主处理。新增角色等功能按本地提取的Skill指导开发，运行契约和效果仍须匹配发行核验；不将关卡或简单规则Skill当作新角色替代方案。来源与提取边界见 [功能清单](../../../docs/community-skill-extraction.md)，不依赖外部大Skill或游戏内模组编辑器。

验证引导行为：用 [需求案例](references/scenarios.md) 检查是否提出正确的必要问题、避免重复询问、正确组合路由。实现后的运行验收必须转入[pvzhe-mod-verify](../pvzhe-mod-verify/SKILL.md)，读取本轮相关参考，不自行省略为启动脚本。功能验收要回应用户描述的效果，不能只报告编译成功。

创建自有浮动UI即组合[pvzhe-ui-drag](../pvzhe-ui-drag/SKILL.md)，不以玩家提出换位置为前提。AI自主安排初始位置并在首次交付时主动告知中键拖动、松开永久保存、发布后仍可用。当前开发任务中，用户拖动是位置调整反馈，先核对本轮目标Mod/控件来源，再更新项目默认布局，不再要求文字请求或二次确认。固定/不可拖动的明确要求仍尊重；旧placement-preview仅兼容明确指定的旧流程。

用户明确说更新/同步官方模板时路由到[pvzhe-project-update](../pvzhe-project-update/SKILL.md)，保护已有Mod身份和功能；只有维护者要求研究新版游戏兼容迁移才用template-upgrade。普通功能开发不自动升级模板或更换.game环境。

用户说“给我的Mod加版本更新”、提供社区投稿链接或要求填写postId时，走mod-develop的[社区投稿关联](../pvzhe-mod-develop/references/community-updates.md)，不误触发模板更新；缺少该Mod自己的投稿信息再询问。
