# 先理解需求，再选择实现

玩家不需要知道组件、接口或 Skill 名称。输出是足够明确的需求摘要、必要问题及制作路由，不是让玩家填写技术问卷。

项目定位是最小模板和通用制作指导。FeatureLab 仅是可选参考与实测证据；按当前需求选择必要功能，不把示例整套内容当作玩家默认要求。

创建新 Mod 时，在主题明确后按 [身份与发布规范](../pvzhe-mod-develop/references/identity-and-release.md) 主动拟定稳定 ID；名称可建议、作者由用户指定。已有 Mod 添加功能不改身份。用户有分享/发布意图时先补齐并确认名称、作者、版本，再做发布检查；本地开发不为待确认署名阻塞无关工作。

1. 结合当前对话和项目识别玩家要看到的效果、使用场景、触发方式及作用范围。保留已确认的选择，不重新询问已有答案。
2. 区分关键缺项与实现细节。缺项会改变玩家得到的功能，且不能从上下文合理推断时，先询问；资源路径、原版风格组件选型、事件订阅和清理由 AI 分析决定。不要先要求玩家选择原版组件。
3. 每轮优先问最影响方向的 1～3 个问题，使用玩家语言。用户只说“加个按钮”时，先问放哪里、点击做什么；文字可随后确认或依据用途建议。不要凭空实现一个按钮，也不要一开始询问字体、坐标、程序集等技术细节。
4. 对合理默认值简短说明后继续，不要求批准每个细节。对局右下角击杀数已有位置和内容，先分析统计口径；“所有敌方僵尸死亡”和“仅玩家造成的击杀”影响结果，无法推断时询问。不能把离场、读档或销毁默认为击杀。
5. 将目标、场景、触发、行为、数据口径、持久化和验收结果整理成简短摘要。未解决的关键问题保持待定；可先分析接口，但不开始依赖答案的实现。若多个用户需求可独立完成，继续不依赖缺项的部分。
6. 需求足够明确后读取对应制作 Skill，复杂需求可以组合：UI→pvzhe-ui-create；对局展示/统计→pvzhe-battle-hud；设置→pvzhe-mod-settings；战斗规则→pvzhe-gameplay-feature；关卡→pvzhe-level-create。发布/构建问题使用原有 release-analyze/mod-develop/mod-verify。

组件复用由 AI 默认评估，读 [复用资料](../../../docs/reuse-catalog.md)。制作 Skill 若发现新歧义，返回此引导步骤；常规实现选择自主处理。植物与新角色行为本阶段尚无完整方案，不将关卡或简单规则 Skill 当作替代支持。

验证引导行为：用 [需求案例](references/scenarios.md) 检查是否提出正确的必要问题、避免重复询问、正确组合路由。功能验收要回应用户描述的效果，不能只报告编译成功。
