# 社区 Skills 采纳可行性与改造建议

日期：2026-10-18。审阅对象为 [josnil/pvz-hybrid-mod-skills](https://github.com/josnil/pvz-hybrid-mod-skills/tree/50d2ee426bc217f6b194801b9ffbb97b1aaa9f9f)，固定提交 `50d2ee426bc217f6b194801b9ffbb97b1aaa9f9f`。结论只针对这一快照。

**后续状态更新**：用户明确要求提取功能后，已按 [功能提取清单](community-skill-extraction.md) 建立十个专职入口并补充原有Skills。本文保留工具移植障碍和研究建议；其中“暂不建立制作Skill/不路由”的早期安排不再作为阻止使用新指导的规则，具体运行能力仍未因文档提取而获验收。

随后已独立完成 [0.30最小制作路径验收](skill-audit-0.30.0.md)，修正版本字段、注册与指导缺口。本文其余内容保留初始静态审阅范围，最新运行边界以该验收记录为准。

## 1. 范围、证据与结论

覆盖全部3个Skill的主题与关键流程、12篇references、1份植物需求清单，以及相关构建/检查/补丁/设置/地图/角色/素材工具族。进行了文本阅读、文件存在性检查，以及使用本地标准库的Python语法、csproj XML解析；没有导入或执行社区脚本，没有构建其项目、加载游戏程序集、启动游戏或进行交互。本报告不是全部脚本的逐行安全审计，也不是兼容性验收。

**整体可采纳，但应提取方法与小模块，不能直接安装整套流程。** 最有价值的是设置离线校验、产物/负向验证、资源依赖分析和角色组件链路。角色制作技术资料很丰富，但包协议、伴随类型、动画与运行阶段都有未闭合的发行依赖。静态分析时尚未提取角色制作入口；随后已按用户要求提取，见上方状态更新。Hello World、单DLL允许名单与发行版输入保持不变，具体角色运行能力仍待验收。

本报告分类：

| 分类 | 含义 |
| --- | --- |
| A：流程可吸收 | 可归纳到现有指导；不表示社区游戏事实已获本模板验证 |
| B：优先改造工具 | 边界清楚，适合先做离线工具原型和负向夹具；本轮未实现 |
| C：隔离研究 | 有参考实现，但要建立当前发行契约和最小实验，不能进入默认模板 |
| D：后置 | 收益存在但依赖多、范围大，等基础能力稳定或具体需求出现 |
| E：不沿用 | 作者工作区/平台约定、过度绝对化结论或与本项目边界不相容的部分 |

## 2. 先解决的移植障碍

这些是本次仓库静态检查发现的具体问题，不只是一般性顾虑。

| 障碍 | 仓库证据 | 对采纳的影响与改法 |
| --- | --- | --- |
| 路径适配依赖缺失 | 多份Python文件无条件 `from _env import ...`；当前快照不含 `tools/_env.py`，也未找到文档所述的部分 `_gen.py` | 不能只替换一条作者路径就运行。去掉对作者工作区的导入，改用本模板release.json、版本缓存及显式输入；可选经典素材路径单独传入 |
| 项目文件不是合法XML | 7份csproj中6份在 `<Project>` 前被插入Python适配块，标准XML解析在首行失败；仅settings-validate项目通过XML解析 | 不直接复制角色/地图项目。基于本模板干净csproj重建，迁入必要C#源文件、明确共享源与引用；先检查格式再编译 |
| 检查器规则过时 | [verify_pmod.py L247](https://github.com/josnil/pvz-hybrid-mod-skills/blob/50d2ee426bc217f6b194801b9ffbb97b1aaa9f9f/tools/pmod-toolchain/verify_pmod.py#L247) 将托管包限定为schema=2/API=1；本模板默认清单schema=3，FeatureLab API=3 | 不能接入后把现有合法包判坏。保留本模板身份策略，接口上限由prepare获得，资源规则按匹配发行版建立，不拼接新旧规则表 |
| 构建包含安装副作用 | [build_pmod.py L299附近](https://github.com/josnil/pvz-hybrid-mod-skills/blob/50d2ee426bc217f6b194801b9ffbb97b1aaa9f9f/tools/pmod-toolchain/build_pmod.py#L299) 在目标Mods存在时复制包；部分流程还写启用状态 | 拆成生成、校验、打包、显式安装；默认只输出到工作目录，不动玩家Mods、存档或启用文件 |
| 版本与经验混合 | README以V0.28为入口，通用Skill后段包含0.29/0.30和后续调试记录；源码行号和两个构建目录属于作者环境 | 每条技术结论绑定发行摘要/来源/验证状态，不把“更新更勤的文档”当冲突裁决依据 |
| 语法可解析不等于可运行 | tools下64份Python均通过ast语法解析，但仍有上述缺模块与发行依赖 | 不能引用“64份通过”宣称工具可用。后续分别验证依赖完整、无副作用导入、实际命令和产物 |

XML失败的6个项目分别位于：`tools/map/runtime_src/`、`tools/plant/runtime_src_plant/`、`tools/zombie/runtime_src_zombie/`、`runtime_src_zombie_nailong/`、`runtime_src_zombie_sunflower_queen/`、`runtime_src_zombie_super_gatling/`。本轮只解析文本，未尝试修补或编译它们。

## 4. 植物与僵尸：可行路线及依赖

来源：[植物Skill](https://github.com/josnil/pvz-hybrid-mod-skills/blob/50d2ee426bc217f6b194801b9ffbb97b1aaa9f9f/skills/pvz-hybrid-plant-authoring/SKILL.md)、[僵尸Skill](https://github.com/josnil/pvz-hybrid-mod-skills/blob/50d2ee426bc217f6b194801b9ffbb97b1aaa9f9f/skills/pvz-hybrid-zombie-authoring/SKILL.md)。两条路线共享资源协议/角色加载/素材基础，不应各复制一份工具链。

| 能力 | 价值与可行性判断 | 必要改造与未来验收 |
| --- | --- | --- |
| 新植物复用原版外观、只改一个属性 | 最适合作为植物第一阶段，C；看起来改动小，但仍依赖新身份与角色加载 | 选普通、依赖少的基底，不从复杂模仿者/大招样板起步；隔离Key/saveKey/卡片/本体/精灵，验证创建、选取、种植、实际属性、原角色未改变 |
| 修改已有角色与新增角色 | 两种需求必须分开 | 覆盖用明确overrides、冲突与禁用恢复；新增用自己的身份。不能为改一个数值默认新建角色，也不能为了新角色覆盖原版 |
| 角色壳场景、CompanionOnly与同名类型 | 关键前置研究，C；社区有纯数据建议，也有后段要求伴随DLL的修正 | 先核对当前发行是否存在该绑定路径、类名解析和继承约束、回退行为。不能先承诺“新植物纯资源即可”，也不能把某个角色结论推广到所有资源类型 |
| 植物ComponentSet与发射定义 | 高价值，C | 核对继承/父组件集、字段赋值顺序、实际组件实例；存在声明不证明正常射击。模板只生成需求所需差量，防止继承原行为后又执行插件导致双发 |
| 动画事件→开火→Marker2D→子弹 | 高价值，C | 分别核对动画片段、事件命令、生成点类型/路径、朝向与伤害。社区“只有动画没子弹的唯一原因”只能降为候选诊断，不照搬绝对结论 |
| 概率、逐颗连射、持续技能 | 有代码参考但不宜第一阶段，D | 计时、暂停、离场取消、实体去重及负载上限参数化；复用游戏确定性随机优先，单人/主机/联机契约明确，不把真随机当全模式优点 |
| 植物卡库、图鉴、可种植规则 | 用户入口重要，C | 只有加载或直接生成不算可用；校验卡牌/图鉴身份、价格/冷却、解锁、种植条件。只做本Mod作用域，不照搬debug全开或改全部卡库 |
| 新僵尸复用普通基底 | 僵尸第一阶段，C | 先原外观、正常行走/啃食/死亡，再增加护具或发射；不能复制大型投掷/BOSS样板作为所有僵尸的起点 |
| 护具、脱落、暴走 | 中等复杂度，C | 识别护具数据、槽名、媒体和状态机关系；优先宿主机制，但不固定Paper/68等样板值。验证伤害归属、脱落表现、状态切换与死亡 |
| 发射僵尸与目标检查 | 复杂度较高，D | 验证数据侧组件是否已驱动；确需插件时使用自己的生命周期。不能因某种僵尸没有动画发射链就断言所有僵尸必须每帧手动开火 |
| 根运动、移动速度、控制效果 | 有用的诊断线索，C | `_ground`是社区指出的关键源，需按基底核对；不能只加walkSpeed字段或按整树timeScale兜底。Buff需验证持续、恢复、叠加与离场，不顺带冻结所有实体 |
| 换头与部件跟随 | 有完整几何思路，C/D | 先验证父精灵代绘、插层、坐标链及更新时序；保留用户确认位置，区分相对当前倍数与重新定标，不硬编码偏移和阈值 |
| 多体节BOSS/共享血条 | 高依赖，D | 等单角色链路稳定后单独做需求、碰撞、部件生命周期与血条验收；不作为本轮组件库目标 |
| 自制皮肤本地/CPU渲染修复 | 有专门共享实现，C | 参数以资源/实例作用域识别，不用示例名称模糊匹配；核对实际属性与GPU路径，限定已知受影响实例，避免默认周期全树扫描或影响原版 |

“原版表现优先”和“数据优先”是决策起点，不是禁止自定义或禁止插件；最终以需求和发行证据选型。对仅改变数值的需求，不默认询问所有美术字段；需要新外观时再确认已有素材和授权。

## 7. 与当前模板的接缝

1. **保留根构建入口。** 当前`manifest()`要求required运行DLL，`build()`按自有resources允许名单打包，`check_package()`只做当前单DLL形态核验。增加资源型支持须显式分型并验证清单、路径派发与注册；不能仅删去DLL要求。可选项目配置只解决项目选择，不解决资源加载或自定义验收。
2. **保留prepare与缓存。** 外部工具的UNPACK/GAME/REF_DIR统一适配为本模板发行证据和按需资源缓存；反编译、二进制资源恢复等确有需要时再选工具并记录来源，不能把恢复源码树设为所有玩家前提。
3. **原版引用与包内引用分开。** 当前宿主res://资源可直接复用；未来包内场景/资源的相对路径、UID、script与依赖通道必须建立发行契约。资源“被打包”不等于“注册成功”。
4. **校验能力分层。** 包身份/路径用现有Python；实际宿主类型/声明校验用受控离线.NET探针；UI/动画/命中/业务用后续运行证据。探针若依赖原生Godot服务不能冒充纯离线功能。
5. **不扩大自动权限。** 生成、安装、启用、清缓存、进程控制和发布分别处理。构建默认不影响玩家环境，脚本导入不执行清理/安装，测试只写忽略目录与明确隔离数据。
6. **测试跟随输入版本。** 社区源码路径/版本号不足以证明与玩家包一致，规则、样板和报告记录PCK/DLL摘要；mtime或固定“全部PASS”文字不替代身份。

## 8. 建议落地顺序与完成标准

以下是后续实施建议，本轮未执行。未通过前一阶段的关键前置，不宣称下一阶段已支持。

| 阶段 | 最小交付与依赖 | 离线可做的完成标准 | 仍需后续游戏验证 |
| --- | --- | --- | --- |
| P0 整理来源与接缝 | 本报告、外部快照/许可/静态障碍、现有规则去重 | 三Skill及参考/工具去向可追踪，主Skill不整体导入外部流程 | 无新增游戏能力可宣称 |
| P1 设置校验＋通用验证基础 | 独立声明校验、正/负/缺API夹具；采集与报告分离、每轮产物快照 | 本地小程序能区分声明错误/环境错误；报告用存档证据重判不启动游戏；缺证据不写通过。若宿主校验不可离线调用则停在明确限制，不回退为“总是OK” | 设置页显示、保存、即时/重启生效与恢复 |
| P2 一个资源类型 | 优先研究已有投射物单属性差量或其他低依赖类型；选型依当前发行协议 | 自有资源、引用闭包、声明/覆盖目标、允许名单、确定性包和损坏负例；确认无游戏资源整体搬运 | 实际注册、效果、原对象范围、冲突及禁用恢复；不能仅凭静态声明上线 |
| P3 一种最小植物 | P2的资源基础＋角色壳/伴随契约；原外观单属性，不带新动画 | Key/配置/卡片/精灵/必要DLL与依赖一致，编译与入口/类型条件可查，普通加载包与夹具分离 | 可见入口→选卡→种植→正常行为/死亡→离场；原植物不受影响 |
| P4 一种最小僵尸 | 复用P3共享基础，先普通移动/攻击/死亡，再单独护具 | 僵尸配置/护具/组件/身份一致，按实际基底检查移动源 | 移动、啃食、受击、护具/死亡表现与结算 |
| P5 专项扩展 | 逐项增加发射、动画转换、换头、地图、BOSS或移动端 | 专项转换/几何/负向检查；只引入需求所需模块 | 跨状态动画、输入设备、性能、网络权限及宿主共存 |

P2的纯资源方案如果当前协议或分发边界不适合，可改选已验证公共服务支持的托管最小例；不能为了坚持社区路径放松边界。P3是否必须Companion DLL由发行调查决定，不把纯资源作为预设成功路线。

## 9. 文档与 Skills 如何组织，避免变成另一部百科

**当前已按用户要求提取制作Skill，详见功能提取清单。** 可以用这些入口分析并制作新功能；尚未验证的规则不要写入0.30.0 Wiki当成事实，也不因入口存在就承诺所有角色/模式已支持。

后续采用时：流程判断归现有mod-guide/develop/verify/settings的短步骤；已核实的资源/角色/动画契约归对应版本主题页；可运行配方归独立examples目录；探针/纯函数工具归tools；正负例归tests。可复用小模块确有第二个使用者再放Components/Adapters，不先建完整组件库。

植物与僵尸共同基础写一次，各自Skill仅保留专有选择和入口。发布、素材、动画、护具、BOSS按需引用，不把全部references默认加载。路由已向新指导开放，实际制作时先核对本任务契约，并逐项记录构建和运行结论。

采用外部代码时建立小型来源清单：来源提交、原文件/章节、用途、改动、许可证/署名、适用发行、验证状态。可保留MIT代码及所需许可，不以改名或重排目录抹掉来源；游戏原始资源、经典素材、第三方图像/音频的权利单独核对，不能被仓库MIT一并覆盖。

## 10. 最终建议

优先投入P1，再选一个P2实验；不要先搬三份Skill、整套生成器或大型美术库。通用指导只吸收可以改变决策的原则；游戏字段和修复配方待版本核实；作者环境约定不继承。这样既能利用社区已经积累的知识，又不把其历史包袱、环境副作用和未验证承诺带给玩家。
